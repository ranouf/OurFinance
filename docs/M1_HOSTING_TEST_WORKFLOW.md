# M1 — déploiement manuel de Hosting de test

Le workflow `test-hosting-deploy.yml` ne s’exécute que par `workflow_dispatch`, cible uniquement le projet `ourfinance-test` et déploie uniquement **Hosting**. Il ne publie pas les règles Firestore, les index ni le Worker et ne cible jamais la production. Il construit `public/app-config.json` depuis les identifiants Web du projet de test ; ce fichier est ignoré par Git. L’API key Web Firebase est nécessairement distribuée au navigateur et ne doit pas être assimilée à une clé de service.

L'identité de déploiement Hosting observée est dédiée à `ourfinance-test` ; son secret Actions `TEST_FIREBASE_DEPLOY_SA_JSON` est actuellement au niveau du dépôt, alors que le job utilise l'environnement `test`. La réduction de cette portée est suivie dans [#154](https://github.com/ranouf/OurFinance/issues/154). Ne jamais utiliser `FIREBASE_SERVICE_ACCOUNT_JSON` du Worker ni publier une valeur de secret. Vérifier les variables Actions `TEST_FIREBASE_PROJECT_ID`, `TEST_FIREBASE_APP_ID`, `TEST_FIREBASE_AUTH_DOMAIN` et le secret Web `TEST_FIREBASE_API_KEY`. Le workflow refuse tout autre ID/domaine de projet.

Le workflow a déjà servi pour des previews et le site TEST principal, mais la version principale actuellement observée ne porte pas CSP ni `X-Frame-Options` malgré `firebase.json` ; la dérive est suivie dans [#152](https://github.com/ranouf/OurFinance/issues/152). Une nouvelle publication attend la validation visuelle du SHA UI cible.

Pour toute exécution future, fournir le SHA complet, le lien d'une réservation TEST récente dans #30, le lien d'un commentaire d'accord visuel pour **ce même SHA et canal** (`preview` ou `live`) dans #30 ou #122, et le canal. Le workflow ne démarre que depuis `main` avec le compte propriétaire, vérifie la CI du SHA exact, extrait ce commit, réserve la concurrence TEST commune aux autres déploiements et refuse `live` si le SHA n'est pas dans l'historique de `main`. La preview reste isolée et expire après un jour. Après `live`, les en-têtes de `/` et `/dashboard` sont contrôlés ; inspecter aussi les écrans réels, l'authentification et la provenance de la version dans #30. Le commentaire d'accord est une trace de décision, pas une preuve technique de correspondance visuelle. Aucune exécution de ce workflow n'est demandée par cette documentation.
